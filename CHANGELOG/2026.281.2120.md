# 2026.281.2120 — fix(candy): export the VITS data dir and add a synthesis check so the README example runs

## Summary

The candy's only documented synthesis invocation could not run, for a **second and independent**
reason beyond the flag #3 fixed: `vits-piper-en_US-lessac-high` speaks espeak-ng phonemes, and
`sherpa-onnx-offline-tts` cannot find the phoneme data by itself (it exits 255 with
`InitFrontend:403 Not a model using characters as modeling unit`).

**The premise of #5 is wrong, and the measurement says so.** The candy *already* bakes the
espeak-ng data — it ships **inside** the voice tarball the plan already extracts, landing at
`<model dir>/vits-piper-en_US-lessac-high/espeak-ng-data`. What was missing is that nothing
**exported or named** it, so no documented invocation could pass `--vits-data-dir`; and because
the plan asserted **file presence only**, an image whose voice cannot synthesise passed 100% of
its checks. The fix is therefore not a new download — it is the exported contract, the
documentation, and a check that actually synthesises.

Head `23307d8370335a39850e5704f1ed827621101bd3`.

### Why no second download of `espeak-ng-data`

The `tts-models` release does carry a separate `espeak-ng-data.tar.bz2`, and fetching it would ship
the same ~5 MB phoneme tree **twice** inside the image (once inside the voice directory, once
beside it) while adding a second, independently-drifting source for the same bytes. The data
shipping inside the voice asset is upstream's own layout for piper voices, so this PR keeps that
one copy and turns its presence into a check (`vits-espeak-data`) instead of duplicating it.
